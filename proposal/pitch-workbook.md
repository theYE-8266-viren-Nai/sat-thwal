# Pitch Workbook: UIT-First Student Welfare System

## Narrative Frame

Use this workbook to keep proposal language consistent across slides, demos, written proposals, and stakeholder conversations.

Primary frame: Set Thwal is a UIT-first, school-supervised e-government student welfare pilot.

Avoid framing it as:

- A general student marketplace.
- An AI-first consumer discovery app.
- A provider-led advertising platform.
- A fully open public directory.

Lead with:

- School administration control.
- Verified student access.
- Approved provider participation.
- Request oversight.
- Public-service reporting value.

## Audience-Specific Message

### UIT Administration

Set Thwal gives UIT a controlled digital channel for student welfare coordination. Administrators can verify student access, approve providers, monitor service requests, and understand welfare demand across housing, transport, food, and academic support without treating student support as an unsupervised marketplace.

### Students

Set Thwal helps verified UIT students request support from school-approved service providers in one place. The system is designed to make everyday needs easier to handle while keeping the school aware of unresolved welfare issues.

### Providers

Set Thwal gives approved providers a formal way to serve eligible UIT students through a supervised school channel. Participation depends on administrative approval and ongoing service quality.

### Public-Sector Stakeholders

Set Thwal creates a repeatable model for digital student welfare delivery. It strengthens transparency, reduces informal coordination, and gives schools better data for planning services around student needs.

### Demonstration Reviewers

Set Thwal should be evaluated as a governance and welfare coordination pilot. The important question is not only whether students can discover services, but whether the school can supervise eligibility, provider approval, request status, and category-level demand.

## Slide Outline

### Slide 1: Title

Set Thwal: UIT-First E-Government Student Welfare Pilot

Subtitle: Verified students, approved providers, school-supervised requests.

### Slide 2: The Current Gap

Student welfare needs are handled across informal chats, phone calls, and manual referrals. UIT has limited visibility into who needs support, which providers are trusted, and whether requests are resolved.

### Slide 3: The Pivot

Set Thwal moves from a student marketplace concept to a school-centralized public-service system. The university becomes the supervising authority for access, providers, and request outcomes.

### Slide 4: Governance Model

UIT verifies students, approves providers, monitors requests, and reviews service activity. Providers do not enter the system as an open marketplace; they participate through administrative approval.

### Slide 5: Student Workflow

Verified UIT student signs in, selects a welfare category, submits a request, and tracks status. The request becomes visible in the school oversight layer.

### Slide 6: Provider Workflow

Provider registers, submits required details, waits for administrative review, and serves students only after approval.

### Slide 7: Admin Workflow

Admin reviews students and providers, monitors pending and confirmed requests, checks completion signals, and identifies unresolved demand.

### Slide 8: Welfare Categories

Tutors, hostels, food, and transportation are organized as public-service support categories under one school-supervised system.

### Slide 9: Pilot Success Measures

Track verified student adoption, approved provider count, request volume, request completion rate, unresolved requests, and category-level demand.

### Slide 10: Public-Service Outcome

UIT gains a transparent welfare coordination channel with better oversight, safer provider access, and practical data for student support planning.

### Slide 11: Replication Path

After the UIT pilot validates verification, approval, request tracking, and reporting, the same governance model can be adapted for other schools or education departments.

## Demo Talk Track

1. Show that access begins with UIT student verification.
2. Show that services come from approved providers, not an open directory.
3. Submit a student request and explain that it creates a status-tracked welfare record.
4. Open the admin view and emphasize request oversight.
5. Explain how demand data helps UIT plan services and identify gaps.

## Proposal Checklist

- The first paragraph names UIT and school administration.
- The pitch names the work as an e-government/student welfare pilot.
- Student verification appears before provider discovery.
- Provider approval is described as mandatory.
- Admin oversight is described as a core workflow, not a back-office extra.
- Request status and completion tracking are included.
- Public-service value is explicit.
- AI or SmartMatch is secondary to governance and welfare coordination.
- Expansion beyond UIT is framed as a later replication model.
- App-code changes are not promised as part of the docs-only pitch workstream.
